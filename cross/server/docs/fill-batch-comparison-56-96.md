# Сравнение DLX и CSP на 56 и 96 шаблонах

Дата: 12 октября 2026. Источник настроек — задание **129**, выпуск **77**,
56 шаблонов. Второй набор — загрузка выпуска **78**, 96 шаблонов; задания
заполнения для него на момент теста не было, использованы настройки №129.

## Методика

- Один загруженный контекст словаря/геометрии/статистики для обеих стратегий
  каждого выпуска. Фильтр 1, `unique=true`, `shuffle=true`, `lcv=true`,
  `maxNodes=200000`, `restarts=2`, `parallelRestarts=1`, балансировка `cost`,
  `editionHotBan=false`. Дополнительного ограничения в 10 секунд нет.
- Используется рабочая `solveSingleTemplateForReview`, а не упрощённый
  собственный алгоритм балансировки. Сохранены сортировка сложности, соседи,
  ограничения повторов, каскад hard/soft/base, адаптивный и соседний fallback,
  приоритет использования слов и последующая cost-полировка.
- Внутренние бюджеты probe/strict-limited остаются такими же, как в рабочей
  цепочке. Например, probe имеет свой короткий лимит; отсутствие пользовательского
  `maxMs` не означает, что эти этапы не ограничены по времени.
- DLX использует установленную улучшенную Rust-сборку с прежней взвешенной
  эвристикой. CSP включает MAC/распространение ограничений. В основном поиске
  CSP `firstSolution=false`, чтобы сохранять оптимизацию найденного заполнения.
  В коротком probe оба движка останавливаются на первом корректном решении.
- Важное различие от текущего выбора CSP в приложении: probe также использует
  выбранный движок. Рабочий сервис пока всегда выполняет этот этап через DLX.
  Без переключения probe большинство простых сеток были бы заполнены DLX до
  вызова CSP и сравнение стало бы сравнением DLX с самим собой.
- Для выпуска 77 порядок профилей DLX→CSP, для 78 — CSP→DLX. Порядок шаблонов
  одинаков; состояние использованных слов отдельное для каждого профиля.
  После первых решений конкретные исключённые слова закономерно различаются.
  Сравнивается одна политика, не идентичный словарь на каждом последующем шаге.
- Один прогон каждой пары, не многократный статистический эксперимент.
  Все ответы проверены на принадлежность замороженному словарю, полное число
  слотов и отсутствие повторов внутри отдельного шаблона.

## Скорость и успешность

| Набор | Движок | Заполнено | Чистое время решателя | Обработка с подбором определений/изображений | Медиана / P95 решателя на шаблон |
| --- | --- | ---: | ---: | ---: | ---: |
| 56 | DLX | 56/56 | 14.009 с | 18.006 с | 49 / 411 мс |
| 56 | CSP + MAC | 56/56 | 0.854 с | 3.680 с | 15 / 18 мс |
| 96 | DLX | 96/96 | 125.434 с | 135.170 с | 159 / 7725 мс |
| 96 | CSP + MAC | 96/96 | 3.004 с | 9.535 с | 18 / 41 мс |

По суммарному времени решателя CSP быстрее в этих прогонах примерно в **16.4×**
и **41.8×**. Большую разницу дают редкие долгие поиски DLX; медианы отличаются
примерно в 3.3× и 8.8×. Время обработки включает получение данных для review,
но не построение финальных SVG/ZIP и не запись статистики в базу.

## Повторы

| Набор | DLX: дополнительные повторные использования | CSP: дополнительные повторные использования |
| --- | ---: | ---: |
| 56 | 0 | 0 |
| 96 | 38 | 0 |

Повторы DLX на 96 шаблонах возникли **между шаблонами** после разрешённых
fallback-ослаблений, не внутри одной сетки. Распределение дополнительных повторов:
длина 3 — 14, длина 4 — 6, длина 5 — 11, длина 6 — 6, длина 7 — 1.
Никакой запрет повторов в тесте не был специально ослаблен ради одного движка.

На 96 шаблонах DLX решил 77 сеток в probe, 17 в strict и последние 2 через
адаптивный/соседний fallback. CSP решил 95 в probe, оставшуюся — в strict;
поэтому ослабление глобальной уникальности ему в этом прогоне не понадобилось.

## Баланс использования слов

Чем ниже средняя историческая частота выбранных слов, тем меньше опора на
уже часто использовавшиеся ответы. Это не единственный показатель качества.

| Набор | Средняя частота: DLX / CSP | Слов выше исторического hard-порога своей длины: DLX / CSP |
| --- | ---: | ---: |
| 56 | 74.710 / 74.760 | 24 / 20 |
| 96 | 73.779 / 73.493 | 64 / 59 |

Баланс сопоставим, а не драматически лучше у CSP. На 56 шаблонах общая средняя
почти одинакова; CSP немного лучше по числу наиболее часто использованных слов.
На 96 средняя CSP примерно на 0.4% ниже. По длинам есть взаимные уступки:

| Длина | 56: DLX / CSP | 96: DLX / CSP |
| --- | ---: | ---: |
| 3 | 115.31 / 115.51 | 112.88 / 112.68 |
| 4 | 92.85 / 93.94 | 92.78 / 93.04 |
| 5 | 87.35 / 87.21 | 86.66 / 86.06 |
| 6 | 53.73 / 53.74 | 53.76 / 53.06 |
| 7 | 27.82 / 26.27 | 29.04 / 29.65 |
| 8 | 13.01 / 11.62 | 14.49 / 13.65 |

Таким образом, наблюдаемый выигрыш CSP — прежде всего скорость и меньше
fallback-повторов, при сохранении сопоставимого баланса. Эти результаты
поддерживают переход на **протестированный профиль CSP + MAC**, включая его
использование в probe, а не лишь замену значения `engine` в форме.

## Воспроизведение и безопасность

```sh
pnpm run test:fill-batch-solver-comparison /private/tmp/megacross-56-96-comparison.json
```

Скрипт читает исходные данные и создаёт локальный JSON-отчёт с каждым шаблоном,
выбранными словами, временем, fallback-метриками и статистикой по длинам.
Он не вызывает runner/finalize, не создаёт задания, не изменяет выпуск,
FSH/CRW/SVG/ZIP и счётчики использования слов. Движок приложения по умолчанию
в рамках этого сравнения не менялся.

Проверки TypeScript/lint обоих проектов и 12 связанных API/unit тестов прошли.

## Переход на рабочие defaults

После согласования перехода новые API-задания, CLI и общий `solve` по умолчанию
выбирают CSP. MAC включён в основном поиске и коротком engine-aware probe.
Основной поиск сохраняет оптимизацию (`firstSolution=false`), короткий probe
останавливается на первом корректном результате; балансировка/fallback/polish
остаются прежними. Явный `engine=dlx` и CLI `--native-dlx` сохраняют DLX, ранее
сохранённые задания не переписаны. CSP и MAC исполняются в нативном Rust-модуле.

Проверка реальных defaults без подмены профиля:

```sh
pnpm run test:fill-batch-solver-comparison /private/tmp/megacross-csp-defaults-validation.json --production-defaults --engine=csp
```

Повторно получено **56/56 и 96/96**, без повторов внутри сеток и между ними;
чистый поиск — 0.843 с и 4.298 с. Этот прогон не создавал задания и не менял
статистику использования. Локальный backend перезапущен с новыми defaults.
